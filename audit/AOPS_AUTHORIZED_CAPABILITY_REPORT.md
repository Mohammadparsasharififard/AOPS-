# AoPS Authorized-Archive Capability Report

> Generated by inspecting the MathVault architecture after extending it
> to support an **authorized source** scenario. This is a CAPABILITY
> report — not a real audit (which would require an actual evidence
> file from AoPS).

## Summary

The MathVault architecture now supports an authorization layer that
allows a user to opt-in to browser-based fetching for sources that
explicitly grant this permission. **All scope flags default to `false`**
— the user must explicitly opt-in to each capability.

The system NEVER:
- Uses CAPTCHA-solving services
- Uses stolen cf_clearance cookies
- Uses third-party challenge-bypass libraries
- Spoofs the user agent
- Crawls outside the authorized scope
- Bypasses robots.txt (always respected)

The system MAY (only with explicit authorization):
- Use a real browser (Playwright + Chromium) to load pages
- Let Cloudflare's JS challenge run naturally (same as a human in Chrome)
- Persist the cf_clearance cookie in the browser session only
- Pause and wait for human verification if a real CAPTCHA puzzle appears

---

## Authorization scope flags

| Flag | Default | What it grants |
|------|---------|----------------|
| `crawl_public_pages` | false | Allow crawling publicly visible pages |
| `archive_public_content` | false | Allow archiving that content |
| `browser_session_allowed` | false | Allow using a real browser (Playwright) |
| `challenge_verification_allowed` | false | Allow Cloudflare's JS challenge to run naturally in browser |
| `discussion_archive_allowed` | false | Allow archiving public discussion threads |
| `asset_archive_allowed` | false | Allow archiving images, PDFs |

**Each flag must be explicitly `true`.** There is no "all of the above" shortcut.

---

## Required conditions for using AuthorizedBrowserFetcher

The `build_fetcher()` factory function returns `AuthorizedBrowserFetcher`
ONLY when ALL of the following are true:

1. `authorization.status == 'authorized'`
2. `authorization.evidence_verified == True`
3. `authorization.evidence_file` exists on disk
4. SHA-256 of the evidence file matches `authorization.evidence_sha256`
5. Authorization is not expired (`expires_at` is in the future)
6. `authorization.scope.crawl_public_pages == True`
7. `authorization.scope.browser_session_allowed == True`
8. Playwright is installed (`pip install playwright && playwright install chromium`)

If ANY of these conditions is false, the factory returns `HttpFetcher`
(the safe default). HttpFetcher does NOT use a browser and will be
blocked by Cloudflare.

---

## CHALLENGE_REQUIRED detection

If a real CAPTCHA puzzle (image, click-X, hCaptcha, reCAPTCHA, Cloudflare
Turnstile) appears, the `AuthorizedBrowserFetcher.fetch()` method returns
a `FetchResult` with `challenge_required=True`. The scheduler records
the URL in the `blocked_url` table with reason `challenge_required` and
continues to the next URL.

The system **never** attempts to solve the puzzle programmatically.
The user must:
1. Set `browser.headless: false` in `source.yaml`
2. Re-run the crawl
3. The browser will open visibly; the user solves the CAPTCHA
4. The cookie persists in the session
5. Subsequent URLs in the same session don't need a CAPTCHA

## What can NOT be archived (even with authorization)

Even with explicit authorization, the system will NOT archive:

- ❌ AoPS Community forum threads (require login → `login_required`)
- ❌ AoPS Classes (paywalled → `paywall`)
- ❌ User-generated content behind authentication
- ❌ Any URL outside `allowed_paths` (config in `source.yaml`)
- ❌ Any URL disallowed by `robots.txt`
- ❌ Private messages (never accessible regardless)
- ❌ Real CAPTCHA puzzles (paused for human, never auto-solved)

## What the user must do to actually crawl AoPS

1. Obtain WRITTEN authorization from AoPS (PDF / signed letter / email)
2. Save it as `sources/aops/evidence/authorization.pdf`
3. Compute its SHA-256:
   ```bash
   shasum -a 256 sources/aops/evidence/authorization.pdf
   ```
4. Edit `sources/aops/source.yaml`:
   - `authorization.status: authorized`
   - `authorization.evidence_file: sources/aops/evidence/authorization.pdf`
   - `authorization.evidence_sha256: <hash from step 3>`
   - `authorization.evidence_verified: true`
   - `authorization.expires_at: 2026-12-31T23:59:59+00:00` (or similar)
   - `authorization.contact: "Name <email@aops.com>"`
   - Set each scope flag explicitly:
     - `crawl_public_pages: true`
     - `archive_public_content: true`
     - `browser_session_allowed: true`
     - `challenge_verification_allowed: true` (only if AoPS's permission
       explicitly covers letting the JS challenge run)
     - `discussion_archive_allowed: false` (unless explicitly permitted)
     - `asset_archive_allowed: true`
   - `browser.enabled: true`
   - `browser.headless: true` (set false if you need to manually solve CAPTCHAs)

5. Install Playwright:
   ```bash
   pip install playwright
   playwright install chromium
   ```

6. Add AoPS to `.env` allowlist:
   ```
   ARCHIVE_ALLOWED_DOMAINS=artofproblemsolving.com
   ARCHIVE_ALLOWED_PATH_PREFIXES=/wiki/index.php/
   ARCHIVE_START_URLS=https://artofproblemsolving.com/wiki/index.php/Main_Page
   ```

7. Run:
   ```bash
   mathvault crawl --dry-run  # see what would be fetched
   mathvault crawl             # real crawl
   ```

If the authorization file doesn't exist, SHA-256 doesn't match, or any
required scope flag is `false`, the system falls back to HttpFetcher —
which gets blocked by Cloudflare — and 0 pages are archived.

## CRITICAL: "Crawl permission" ≠ "Browser session permission"

This is the MOST IMPORTANT rule the user asked me to enforce:

> "اگر مجوز فقط crawl را اجازه داده ولی صراحتاً browser/challenge
> verification را پوشش نمی‌دهد، آن را bypass مجاز تلقی نکن و آن قسمت
> را NOT AUTHORIZED / NOT VERIFIED گزارش کن."

In other words: **if the authorization only permits crawling, but does
NOT explicitly permit browser-based challenge verification, the system
MUST NOT use the browser for that source**. The system falls back to
HttpFetcher, which gets blocked, and the URLs are recorded as
`cloudflare_challenge` in the `blocked_url` table.

The architecture enforces this via the scope flags:
- `crawl_public_pages: true` alone → HttpFetcher only (still blocked)
- `crawl_public_pages: true` + `browser_session_allowed: true` →
  AuthorizedBrowserFetcher used (but JS challenge won't auto-run unless
  `challenge_verification_allowed: true` is also set)

This separation of concerns is enforced at the code level — there is
no way to "smuggle" browser usage without all three flags being true.

## Conclusion

The architecture now supports an **authorized source** scenario where
the user can opt-in to browser-based fetching for sources that have
explicitly granted this permission. Without the explicit opt-in (the
default), the system uses HttpFetcher — which gets blocked by
Cloudflare — and 0 pages are archived.

The user's stated principle is enforced at the code level:
**"Crawl permission" ≠ "Browser session permission"**. There is no way
to use the browser for a source without explicit `browser_session_allowed:
true` AND a verified evidence file. Real CAPTCHA puzzles are NEVER
solved programmatically — the system pauses for human input.
